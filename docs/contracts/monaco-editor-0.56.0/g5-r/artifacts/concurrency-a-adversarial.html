对抗式结论：选 A+，不选原始 A

A+ = MainActor 只拥有 live model 的最小同步核心；所有长任务和 TextKit 后台布局只消费 immutable snapshot。

A+

在当前目标约束下，A+ 最合适

它保留 Monaco 的同步 ITextModel 与同步事件，又不为每次输入增加锁或跨 executor 调度。原始 A 若把解析、全量构建、Diff、LSP 或后台 TextKit provider 一起放上 MainActor，则直接不通过。

攻击 1 · 是否破坏 Monaco 同步语义

A+ 胜出

Monaco 0.56 的 setValue、applyEdits、pushEditOperations、所有读取均为同步方法；createSnapshot 明确标注可异步消费。

A+ 原样映射：live API 同步隔离，后台只拿 snapshot。C 将 live API 改成 await，直接不等价。

攻击 2 · 是否真的“没有 actor hop”

语义通过

Swift 事实：MainActor 的 executor 等价于 main dispatch queue；同一 actor 内同步调用不使用 await，也不跨 isolation domain。

UI 输入已处于 MainActor，因此不存在跨 executor hop。机器指令级成本不由 API 文档证明，仍进入基准验收。

攻击 3 · 大文件和长任务阻塞 UI

原始 A 失败

Apple 明确要求把长时间和资源密集型非 UI 工作移出 MainActor；在 MainActor 内创建 Task 仍继承该隔离域。

A+ 只在 MainActor 做 preflight、Piece Tree 增量 commit、版本、事件和局部 invalidation。文件解码、buffer factory、Diff、LSP 与全量分析全部 nonisolated。

攻击 4 · TextKit layoutQueue 冲突

原始 A 失败

SDK 26.5 明确规定 NSTextLayoutManager / NSTextLayoutFragment 可把布局派发到指定 NSOperationQueue。

后台 provider 禁止捕获 live model、EditorCore、Theme 或 Decoration Tree；它只持有 versioned LayoutSnapshot 与 RenderStyleSnapshot。

攻击 5 · 无 UI / 后台调用是否受限

A+ 的明确代价

后台调用方不能同步修改 MainActor-isolated live model；它必须提交 Sendable EditIntent 并 await MainActor。

当前交付目标是 macOS 编辑器组件，后台同步写 live model 未进入已锁定能力。命令行测试在 MainActor 执行，快照计算仍并行。

攻击 6 · 监听器重入与事件顺序

可完全对标

Monaco 的 Emitter 在重入 fire 时先完成当前 listener 队列，再投递下一事件，保证所有监听器按版本观察变更。

A+ 在单一 MainActor 上实现同样的 delivery queue；B 还要解决跨线程提交、等待和重入的组合问题。

MainActor：只保留同步最小核心

  • live Piece Tree、line index、Decoration Tree
  • EditTransaction preflight 与 atomic commit
  • version / alternativeVersion / undo stack
  • 同步事件 delivery queue
  • Editor cursor、selection、view state
  • 异步结果的 version gate 与 UI 应用

Nonisolated：只处理不可变值

  • 文件解码与 TextBufferFactory
  • MonaTextSnapshot 的遍历与索引
  • LSP transport / JSON-RPC / Provider 计算
  • Diff、搜索预计算、语义 token 转换
  • TextKit layoutQueue snapshot provider
  • 基准采样与结果聚合
