方案 A：对抗式验证结果

目标不是证明方案正确，而是用 Apple SDK 26.5 公共头文件与 Monaco 0.56 源码寻找能推翻它的反例。

A

总架构保留，收紧 3 条边界

唯一文本真源、TextKit 2 首选、可替换后端均成立。输入层不得依赖 NSTextView 的编辑语义；每个 Editor 必须拥有独立 TextKit graph；后端 SPI 必须覆盖布局与渲染，而非只覆盖绘制。

攻击 1 · 直接复用 NSTextView

反例命中

SDK 事实：NSTextView 的 selectedRanges 在多范围时禁止零长度范围；Monaco 的 CompositionOperation 对全部 selections 执行 map，包括多个空光标。

修正：MonaCodeEditorView 是自定义 NSView + NSTextInputClient。系统只感知主光标，EditorCore 将输入、IME composition 与命令复制到 Monaco 等价的全部 selection。

攻击 2 · 多编辑器共享 TextKit graph

反例命中

SDK 事实：textSelections 属于 NSTextLayoutManager；NSTextContentManager 只有一个 primaryTextLayoutManager，编辑事务期间非 primary 的访问会阻塞或失败。

修正：一个 MonaCodeModel 可被多个 Editor 共享；每个 Editor 独占 ContentManager、LayoutManager、ViewportController、selection 与渲染缓存。

攻击 3 · 自有模型无法接入 TextKit 2

未推翻

SDK 事实：NSTextContentManager 明确支持自定义 backing store、自定义 NSTextLocation、按需枚举元素、编辑范围调整与 recordEditAction；ViewportController 明确允许自定义 layer/view surface。

保留：MonaCodeModel 仍是唯一真源，TextKit adapter 只生成视口所需的瞬态 paragraph/layout fragment，不保留第二份可编辑全文。

攻击 4 · 后台布局直接读取 Piece Tree

强制护栏

Monaco 源码事实：PieceTreeSnapshot 自己注明真实多线程读取要求 piece 不可变，且读取期间不得执行 TreeNode/Buffer normalization。

修正：TextKit layoutQueue、Diff、Provider 与 LSP 只能读取带 version 的 immutable snapshot；任何后台路径都禁止读取 live mutable Piece Tree。

攻击 5 · 超长单行仍是“视口增量”

性能关口

SDK 事实：NSTextParagraph 是以完整 NSAttributedString 为内容的单个段落；Monaco 0.56 默认 stopRenderingLineAfter = 10,000。

修正：TextKit backend 必须实现 10,000 UTF-16 单元后的隐藏尾段语义。配置为 -1 或超长行基准落后时，切换 Layout + Render backend。

攻击 6 · TextKit 2 已满足性能目标

尚未验收

当前事实仅证明公共 API 能承载架构；当前仓库没有可执行切片，因此没有 MonaCode 与 Monaco 0.56 的延迟、内存、CPU、GPU、能耗对照数据。

结论：TextKit 2 保持首选后端，但不获得性能豁免。任一独立指标落后即判定该后端未通过，并进入下一后端。
